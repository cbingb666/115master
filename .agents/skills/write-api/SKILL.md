# 编写接口

本 skill 消费 `/reverse-api` 产出的逆向报告，将已确认的接口契约落地到代码。它不负责继续逆向，也不根据猜测补全接口。

## 输入门槛

开始实现前，确认已有证据能够说明：

- 请求身份、方法和参数位置。
- 关键输入的观测类型、来源及可选性。
- 成功响应与已知失败响应的形状。
- 多请求流程的依赖、终止条件和错误语义。
- 尚未确认的推断与未知项。

如果缺失信息会实质改变公开类型、请求构造或控制流，停止实现相关部分，并请用户先调用 `/reverse-api` 补充调查。不要把示例值、字段名直觉或现有错误实现当作事实。

## 实现原则

### 先遵循目标模块

读取根目录及目标 package/app 的 `AGENTS.md`、代码风格和测试指南，再检查现有实现与未提交改动。

优先扩展已有领域边界和抽象。只有现有模块无法自然承载新能力时，才新增目录、客户端或公共概念。不要机械套用固定文件模板。

### 让证据决定类型

- 请求与响应类型只表达已有证据支持的契约。
- 区分字段缺失、`null`、空集合和零值。
- 有稳定判别字段时使用可判别联合表达不同响应分支。
- 未验证字段保持局部，不为“以后可能有用”扩大公共类型。
- 不用 `any` 掩盖未知；无法建模的边界数据先保持 `unknown` 并在边界收窄。

### 隔离传输细节

复用项目既有的请求抽象、响应归一化、错误处理、认证和编码能力。协议中的兼容性分支、别名字段或不一致响应应收敛在边界层，不泄漏给所有调用方。

公开方法按业务意图命名；线路、主机、编码和回退等传输选择留在客户端内部。

### 保持导出边界明确

只导出调用方真正需要的客户端、参数、结果和领域类型。使用显式导出，不创建 `export * from ...`。

新增领域能力时，检查其领域入口、客户端汇总入口、package 根入口和门面聚合是否都需要更新，避免产生只能从内部路径访问的半成品 API。

### 按风险选择运行时校验

当响应来自不稳定边界、字段形状影响控制流，或目标模块已有 schema 约定时，增加运行时校验。不要为了形式完整而复制一套与 TypeScript 类型重复且无人执行的 schema。

## 实现流程

### 固化契约

先把逆向报告转换为实现清单：

- 每个公开方法对应的用户意图。
- 请求参数与线路选择。
- 原始响应到公开结果的映射。
- 业务失败、传输失败和可重试状态的处理。
- 多请求流程中的状态、退出条件和取消行为。

所有未知项必须有处理决定：不实现、隔离为内部兼容逻辑，或由用户补充证据。

### 编写最小纵切

按“类型 → 单个客户端方法 → 导出/门面 → 测试”的纵向切片实现一条完整能力，再扩展其余分支。这样可以尽早发现领域边界、依赖注入或响应归一化不匹配。

不要先批量创建所有类型和文件，再尝试把它们接入运行时。

### 编写测试

使用脱敏后的真实响应形状作为 fixture，并通过目标模块现有的请求抽象注入传输结果。

至少覆盖适用项：

- 最小成功响应。
- 业务失败与传输失败。
- 可选、缺失、`null` 和空值字段。
- 参数放置与编码。
- 多请求流程的顺序、终止和异常退出。
- 回退、重试或幂等行为。

断言公开行为和传输契约，不锁定私有函数或无关实现细节。测试无法证明真实服务仍遵守契约；它只证明代码正确处理已观察样本。

### 编写文档

文档记录已实现的公开能力和证据支持的协议，包括：

- 方法用途与前置条件。
- 输入含义、类型、必填证据和动态值来源。
- 成功与失败结果。
- 多请求流程和状态转换。
- 已知限制、未验证分支与敏感信息处理要求。

示例必须脱敏，不包含真实凭据、Cookie、令牌、签名或个人数据。

### 验证

依据目标模块指令，按改动风险执行类型检查、相关单元测试、lint 和必要构建。

如果实现没有改变 UI，不要把构建成功描述为浏览器验收。只有实际执行并通过对应验证，才能报告该项通过。

## 完成报告

向用户说明：

- 新增或修改了哪些公开能力。
- 关键契约如何映射到类型和控制流。
- 已运行的检查及结果。
- 未运行的验证及原因。
- 保留了哪些未知项，以及它们为何没有被猜测实现。
