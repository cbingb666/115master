# API 逆向

本 skill 提供逆向 Web 接口的思维框架，不提供固定操作步骤，也不复述浏览器自动化命令。

## 工具边界

所有页面观察、交互实验和网络证据采集统一使用 `playwright-cli` skill。具体操作方式以该 skill 为准，不在此重复。

本 skill 只负责调查、推理和整理结论，不创建接口类型、客户端、测试或接口文档。

## 目标

逆向的目标不是找到一个看起来相关的 URL，而是形成一份可验证的接口模型，能够回答：

- 用户意图由哪些请求共同完成？
- 每个输入来自哪里，哪些值是稳定契约，哪些值由运行环境动态产生？
- 成功、业务失败和传输失败分别如何表达？
- 请求之间是否存在顺序、依赖、轮询、并发、取消或重试关系？
- 哪些结论已被观察证实，哪些仍是推断或未知？

## 核心原则

### 证据先于解释

先记录页面行为和网络事实，再解释其含义。不要因为字段名、函数名或既有代码“看起来合理”就把它当成契约。

每条结论标记为以下一种：

- **已观察**：可由一次或多次实验直接证明。
- **推断**：由多条证据支持，但尚未直接验证。
- **未知**：当前证据不足，不能安全下结论。

### 把交互视为受控实验

每次实验只改变一个因素，并与基线比较。优先设计能够排除其他解释的实验，而不是无目的地浏览页面。

一个可靠的实验矩阵通常包括：

- 不触发目标行为的基线。
- 一条最小成功路径。
- 只改变一个输入的对照路径。
- 至少一条失败或边界路径。
- 重复同一行为，用于识别随机值、时间值和会话值。

### 从差异推断因果

通过两次实验之间的差异判断 UI 输入与请求字段的映射。多个字段同时变化时，不能断言其中任何一个字段的含义或必填性。

区分：

- 用户提供的业务输入。
- 页面状态派生的上下文。
- 会话、时间、签名等动态值。
- 与目标行为无关的环境噪声。

### 交叉验证

单一证据源可能误导。重要结论至少尝试由两类证据相互印证：

- 页面行为与状态变化。
- 网络请求与响应。
- 多次受控实验的差异。
- 必要时的运行时代码或前端源码线索。

源码只能说明某个版本可能如何执行，不能代替实际请求证据；网络记录只能说明发生了什么，不能自动说明每个字段为什么存在。

### 把接口视为协议

真实功能往往不是单个端点，而是一个协议或状态机。除了请求与响应结构，还要关注：

- 前置请求产生的值如何进入后续请求。
- 分支条件如何改变请求序列。
- 后台任务如何启动、查询进度和结束。
- 重试是幂等重放、继续任务，还是创建新任务。
- 页面关闭、导航或用户取消后发生什么。
- 并发操作是否共享状态或相互覆盖。

## 调查框架

### 明确问题

先把目标写成可证伪的问题，例如“哪个请求提交了最终变更”或“进度由推送还是查询驱动”。避免使用“找出所有相关接口”这类没有停止条件的目标。

同时记录实验前置状态：页面位置、选中对象、账户能力、功能开关以及其他可能改变分支的条件。

### 建立行为边界

从用户可见结果反推调查范围：

1. 什么动作开始了功能？
2. 什么可观察结果代表成功？
3. 什么结果代表失败、取消或仍在处理中？
4. 哪些请求只负责加载界面，哪些请求真正改变业务状态？

不要把时间上相邻的所有请求都归因于目标行为。

### 识别请求身份

以方法、路径、参数位置和响应角色共同识别请求，不依赖易变化的完整 URL、请求编号或打包后的函数名。

对每个候选请求判断：

- 它是读取、校验、提交、轮询还是辅助请求？
- 缺少它时用户结果是否仍可能出现？
- 相同动作重复执行时它是否稳定出现？
- 它与前后请求通过什么值关联？

### 还原请求契约

逐项判断输入的：

- 位置：路径、查询、请求体、请求头或会话上下文。
- 原始形态：字符串、数字、布尔、数组、对象或编码后的载荷。
- 可选性：始终出现不等于必填；未观察到不等于不存在。
- 来源：用户输入、页面状态、前序响应或运行时生成。
- 稳定性：固定值、枚举值、随会话变化或每次请求变化。

不要复制或输出凭据、Cookie、令牌、签名原文及个人数据。只描述它们的角色、来源和生命周期。

### 还原响应语义

分别研究 HTTP 层、业务层和数据层：

- HTTP 成功是否仍可能表示业务失败？
- 成功与失败是否使用不同的数据形状？
- 缺失、`null`、空集合和零值是否具有不同语义？
- 错误码、错误消息和可重试性如何关联？
- 响应中的哪些值驱动后续请求或页面状态？

只有在多个样本支持时，才能把字段声明为稳定、必有或枚举。

### 还原时序与状态

按因果关系整理调用序列，而不是简单按时间排序。重点识别：

- 请求是否必须等待前序结果。
- 是否存在并行请求及汇合点。
- 查询何时开始、停止以及如何判断完成。
- 中间状态是否可能跳过、重复或倒退。
- 超时、重复提交和页面刷新后的恢复行为。

复杂流程优先画状态转换或时序图，以显式暴露缺失的分支。

### 解释异常与边界

失败路径比成功路径更能揭示真实契约。优先寻找：

- 缺少输入与非法输入的差别。
- 权限不足、会话失效与资源不存在的差别。
- 空结果、部分成功和重复操作的语义。
- 网络失败后页面是否自动重试或允许继续。
- 大小、数量、分页和速率边界。

不要为了触发失败而执行会破坏用户数据或扩大影响范围的操作。

### 收敛结论

当新实验不再改变接口模型，且关键结论都有证据或明确标记为未知时停止。不要为了追求“完整”无限扩展到与用户目标无关的功能。

## 逆向报告

最终输出一份可供实现阶段消费的报告，至少包含：

### 调查范围

- 用户目标与成功判定。
- 前置状态和已覆盖场景。
- 明确未覆盖的范围。

### 行为与证据矩阵

| 场景 | 唯一变量 | 观察到的请求差异 | 页面或业务结果 | 重复情况 |
|---|---|---|---|---|

### 接口契约

对每个请求记录：

- 请求身份与它在流程中的角色。
- 触发条件和前置依赖。
- 输入位置、观测类型、来源及可选性证据。
- 成功与失败响应的实际形状和语义。
- 与其他请求共享的关联值。
- 时序、重试、幂等和终止条件。
- 结论置信度及其证据。

### 流程模型

用简洁的时序图或状态图表示请求之间的因果关系、分支和终止状态。

### 不确定项

- 已观察事实。
- 尚待验证的推断。
- 未知字段或分支。
- 建议的最小后续实验。

## 完成边界

满足以下条件后，逆向阶段才算完成：

- 目标行为与候选请求之间有因果证据，而不只是时间相关性。
- 关键输入至少经过一次差异实验。
- 成功路径和重要失败路径均有样本，或明确记录无法安全验证的原因。
- 动态值与业务输入已区分。
- 多请求流程的依赖和终止条件已说明。
- 所有推断和未知项均被显式标记。

完成后不要自行生成接口代码。向用户提示：

> 逆向结论已整理完成。若要根据这份报告在仓库中实现类型、客户端、测试和文档，请显式调用 `/write-api`。
